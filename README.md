# Техническое задание
## Финальный проект «Умный помощник для конспектирования встреч»

### 1. Описание проекта

Созвонились с коллегами, обсудили вопросы, зафиксировали договорённости и разошлись. На практике так бывает редко: записи встреч теряются, заметки ведутся в разных местах, договорённости фиксируются неполно или не фиксируются вовсе.

«Умный помощник для конспектирования встреч» помогает решить эту проблему: система принимает аудиозапись или тестовый файл встречи, получает текстовую расшифровку, сохраняет результат, индексирует текст для последующего поиска и позволяет задавать уточняющие вопросы по материалам встречи.

Проект должен проверять не только реализацию пользовательских функций, но и инженерные компетенции уровня **Middle Go-разработчика**: архитектурное разделение, заменяемость внешних интеграций, работу с PostgreSQL, асинхронную обработку, конкурентность, обработку ошибок, тестируемость и способность объяснить принятые решения на защите.

### 2. Зачем конспектировать встречи

Конспектирование встреч полезно, потому что:
*   мы забываем услышанное;
*   мы можем искажать услышанное;
*   текстовая фиксация помогает решать спорные ситуации;
*   материалы встреч полезны для новых сотрудников;
*   по сохранённым встречам можно быстро искать важные договорённости, решения и факты.

### 3. Общая идея системы

Система представляет собой backend-сервис для загрузки, обработки, хранения и поиска материалов встреч.

Пользователь может взаимодействовать с системой через один из доступных интерфейсов:
*   CLI-утилиту;
*   VK-бота;
*   Telegram-бота (если этот вариант доступен слушателю);
*   TUI — как дополнительный вариант реализации CLI-интерфейса.

Выбранный интерфейс не должен содержать основную бизнес-логику. Он должен выступать внешним адаптером, который принимает команды пользователя и передаёт их в общий слой приложения.

Основная бизнес-логика должна быть независима от выбранного способа взаимодействия с пользователем и от конкретных внешних API распознавания речи или LLM.

### 4. Основная бизнес-логика

Система должна обеспечивать:
*   загрузку аудиофайлов встреч или тестовых файлов для обработки;
*   создание задачи на обработку загруженного файла;
*   асинхронное получение транскрипции через абстрактный speech-клиент;
*   получение краткой выжимки через абстрактный LLM-клиент;
*   сохранение транскрипции, краткой выжимки, статуса обработки и метаинформации в PostgreSQL;
*   поиск по сохранённым транскрипциям и/или кратким выжимкам;
*   получение списка встреч пользователя;
*   получение полной транскрипции встречи по идентификатору;
*   отправку уточняющих вопросов к LLM-клиенту по сохранённым материалам;
*   разграничение данных пользователей: пользователь должен получать доступ только к своим встречам и результатам обработки.

### 5. Архитектурные требования

Решение должно быть спроектировано так, чтобы были разделены:
1.  Слой пользовательского интерфейса: CLI, VK или Telegram;
2.  Слой обработки команд;
3.  Слой бизнес-логики;
4.  Слой работы с базой данных;
5.  Клиент сервиса распознавания речи;
6.  LLM-клиент;
7.  Слой фоновой обработки задач;
8.  Слой конфигурации.

Клиенты внешних сервисов должны быть описаны через интерфейсы. Бизнес-логика не должна напрямую зависеть от Speech API, GigaChat или любого другого конкретного поставщика API. В проекте должна быть возможность заменить реальный клиент тестовой реализацией без изменения бизнес-логики.

### 6. Абстрактная схема взаимодействия с системой

#### 6.1. Регистрация пользователя
Пользователь начинает работу с системой одним из способов:
*   в мессенджере отправляет команду `start`;
*   в CLI-утилите впервые указывает свой `user_id` при выполнении команды.

При первом обращении система создаёт пользователя и сохраняет его идентификатор.

#### 6.2. Загрузка встречи
Пользователь загружает аудиофайл или тестовый файл:
*   через мессенджер — как голосовое сообщение или аудиофайл;
*   через CLI — передаёт путь к локальному файлу командой `load <path>`.

Система создаёт запись о встрече и задачу на обработку.

> **Тестовый файл** — это файл или тестовый сценарий, для которого заранее подготовлена транскрипция, возвращаемая тестовой реализацией speech-клиента. Использование тестового режима не отменяет создание встречи, задачи обработки, статусов, сохранение результата и прохождение полного бизнес-сценария.

#### 6.3. Обработка встречи
Система должна выполнять обработку асинхронно:
1.  принять файл;
2.  сохранить информацию о встрече;
3.  создать задачу обработки;
4.  передать файл в speech-клиент;
5.  получить или сымитировать результат распознавания;
6.  сохранить транскрипцию;
7.  передать текст в LLM-клиент для получения краткой выжимки;
8.  получить или сымитировать краткую выжимку;
9.  сохранить краткую выжимку;
10. обновить статус обработки.

Пользователь не должен ждать завершения долгой обработки в рамках одного синхронного запроса. Он должен иметь возможность узнать статус обработки отдельной командой.

#### 6.4. Работа с результатами
После обработки пользователь может:
*   посмотреть список встреч;
*   получить транскрипцию по идентификатору;
*   выполнить поиск по ключевым словам;
*   задать уточняющий вопрос по сохранённым материалам.

### 7. Команды системы

Независимо от выбранного интерфейса система должна поддерживать единый набор команд.

#### 7.1. Обязательные команды

*   **`start`**
    Регистрация пользователя. Для CLI регистрация может выполняться автоматически при первом использовании `user_id`.
*   **`load <path>`**
    Загрузка аудиофайла или тестового файла для обработки. Для CLI `path` — путь к локальному файлу. Для мессенджеров загрузка файла или голосового сообщения считается началом обработки.
*   **`list`**
    Получение списка сохранённых встреч пользователя. В результате должны выводиться идентификатор встречи, дата создания, краткое описание или выжимка (если она уже получена) и текущий статус обработки.
*   **`status <id>`**
    Получение текущего статуса обработки встречи. Команда должна показывать идентификатор встречи, текущий статус, дату создания, дату последнего изменения статуса и текст ошибки, если обработка завершилась неуспешно.
*   **`get <id>`**
    Получение транскрипции встречи по идентификатору. Пользователь может получить только свою встречу.
*   **`find <keyword>`**
    Поиск встреч по ключевому слову или фразе. Поиск должен выполняться только по встречам текущего пользователя.
*   **`chat <text>`**
    Передача вопроса к LLM-клиенту и получение ответа по сохранённым материалам. Способ привязки вопроса к конкретной встрече остаётся на усмотрение слушателя.

#### 7.2. Дополнительные команды

*   **`retry <id>`**
    Повторный запуск обработки встречи, завершившейся с ошибкой. Команда не должна повторно запускать обработку успешно завершённой встречи без явного обоснования в логике приложения.
*   **`delete <id>`**
    Удаление встречи и связанных с ней данных. Реализация команды не обязательна, но может быть полезна для демонстрации работы со связанными сущностями и транзакциями.

### 8. Статусы обработки

Для задач обработки необходимо предусмотреть модель статусов.

Минимальный набор статусов:
*   `created` — задача создана;
*   `processing` — задача находится в обработке;
*   `transcribed` — транскрипция получена;
*   `summarized` — краткая выжимка получена;
*   `completed` — обработка полностью завершена;
*   `failed` — обработка завершилась ошибкой.

Допускается использовать другой набор статусов, если он обоснован и позволяет отследить жизненный цикл обработки встречи.

### 9. Варианты пользовательского интерфейса

Слушатель выбирает один основной способ взаимодействия с системой.

#### 9.1. CLI-утилита
CLI-утилита является рекомендуемым вариантом, так как не зависит от доступности внешних мессенджеров и удобна для локального тестирования.

**Требования к CLI:**
*   реализовать CLI-утилиту, которая принимает команды через аргументы командной строки. Можно использовать `cobra`, `flag` или другой обоснованный подход;
*   реализовать загрузку файла по указанному пути из локальной файловой системы;
*   обрабатывать запросы нескольких пользователей через указание `user_id` в аргументах команды или через конфигурацию;
*   создать отдельный модуль CLI-интерфейса;
*   поддержать обязательные команды: `load <path>`, `list`, `status <id>`, `get <id>`, `find <keyword>`, `chat <text>`.

Регистрация пользователя происходит автоматически при первом использовании. Дополнительно можно реализовать TUI.

#### 9.2. VK-бот
VK-бот может быть выбран как основной интерфейс, если слушателю удобен этот вариант.

**Требования к VK-боту:**
*   зарегистрировать VK-бота: создать standalone-приложение и получить токен группы;
*   использовать документацию VK Bot API и библиотеку `github.com/SevereCloud/vksdk` или другой обоснованный подход;
*   реализовать обработчики сообщений и файлов;
*   реализовать загрузку файлов через VK API;
*   обрабатывать запросы нескольких пользователей;
*   учитывать, что в VK нет команды `/start`, как в Telegram. Регистрация пользователя происходит при получении первого сообщения по `from_id`;
*   создать отдельный модуль клиента для VK.

Бот должен обрабатывать события VK Callback API: `message_new`, `message_new` с `audio_message`, `message_new` с `doc/audio`.

#### 9.3. Telegram-бот
Telegram-бот может быть выбран как основной интерфейс только в том случае, если этот вариант доступен слушателю.

**Требования к Telegram-боту:**
*   зарегистрировать Telegram-бота;
*   с помощью библиотеки `gopkg.in/telebot.v3` или другого обоснованного подхода реализовать обработчики сообщений и файлов;
*   реализовать загрузку файлов по сгенерированной ссылке из Telegram;
*   обрабатывать запросы нескольких пользователей;
*   создать отдельный модуль клиента для Telegram.

Бот должен предоставлять обработчики `OnText`, `OnVoice` и `OnAudio` или их аналоги.

### 10. Требования к хранению данных

Хранилище данных — **PostgreSQL**.

Структура таблиц, типы и формат хранения остаются на усмотрение слушателя, но схема должна включать несколько связанных сущностей.

Минимально рекомендуется выделить:
*   пользователей;
*   встречи;
*   задачи обработки;
*   транскрипции;
*   краткие выжимки;
*   ошибки обработки или историю статусов;
*   историю вопросов и ответов (если реализована).

Система должна обеспечивать:
*   связь встречи с пользователем;
*   связь задачи обработки с конкретной встречей;
*   хранение статуса обработки;
*   хранение текста транскрипции;
*   хранение краткой выжимки;
*   хранение ошибок обработки, если они возникли;
*   выборку только тех встреч, которые принадлежат текущему пользователю;
*   индексы для часто используемых запросов: список встреч пользователя, поиск по тексту, получение встречи по идентификатору, получение задач по статусу.

В проекте должны быть предусмотрены миграции базы данных.

### 11. Транзакционность

В проекте должна быть как минимум одна операция, требующая согласованного изменения нескольких сущностей. Например:
*   создание встречи и задачи обработки;
*   сохранение транскрипции и обновление статуса задачи;
*   сохранение ошибки и перевод задачи в статус `failed`;
*   удаление встречи и связанных с ней данных.

Если одна часть такой операции завершается ошибкой, система не должна оставлять данные в неконсистентном состоянии.

### 12. Поиск

Минимальное требование — поиск по ключевым словам в сохранённых транскрипциях и/или кратких выжимках. Поиск должен учитывать права доступа: пользователь не должен видеть встречи других пользователей.

**Обязательный результат поиска:**
*   идентификатор встречи;
*   дата создания;
*   статус обработки;
*   краткое описание или фрагмент текста.

Дополнительно можно реализовать:
*   полнотекстовый поиск PostgreSQL;
*   поиск по метаинформации;
*   поиск по краткой выжимке;
*   ранжирование результатов;
*   подсветку найденных фрагментов.

### 13. Асинхронная обработка и конкурентность

Обработка файлов должна выполняться асинхронно. Система не должна блокировать приём новых команд на время распознавания речи и получения краткой выжимки.

Для фоновой обработки необходимо использовать возможности Go для конкурентного выполнения:
*   goroutines;
*   channels;
*   context;
*   ограничение числа одновременно выполняемых задач.

**Минимальные требования:**
*   после загрузки файла создаётся задача обработки;
*   долгая обработка выполняется в фоне;
*   пользователь может проверить статус задачи командой `status <id>`;
*   количество одновременно обрабатываемых файлов должно быть ограничено;
*   система не должна запускать неограниченное количество goroutines;
*   каждый пользователь получает только результаты своих запросов;
*   ошибки внешних клиентов должны сохраняться и быть доступны через статус задачи.

Дополнительно можно реализовать повторные попытки обработки, команду `retry <id>`, восстановление незавершённых задач после перезапуска и более сложную очередь задач.

### 14. Context, timeout и graceful shutdown

В проекте необходимо использовать `context.Context` для управления временем выполнения и отменой операций.

Требуется предусмотреть:
*   таймауты для внешних API;
*   отмену долгих операций;
*   передачу `context` от транспортного слоя к бизнес-логике и инфраструктурным клиентам;
*   корректную отмену фоновых задач при завершении приложения;
*   graceful shutdown.

При завершении приложения система должна перестать принимать новые задачи, корректно завершить уже выполняющиеся операции или перевести их в согласованный статус, закрыть соединения с базой данных и завершить фоновые goroutines без утечек.

### 15. Обработка ошибок

Система должна корректно обрабатывать ошибки:
*   пользователь передал неизвестную команду;
*   пользователь передал команду без обязательных аргументов;
*   пользователь запросил несуществующую встречу;
*   пользователь запросил встречу другого пользователя;
*   файл не найден;
*   формат файла не поддерживается;
*   speech-клиент недоступен;
*   LLM-клиент недоступен;
*   превышен лимит внешнего API (если используется реальная интеграция);
*   база данных временно недоступна;
*   истёк timeout или операция была отменена через context.

Ошибки должны быть понятны пользователю и не должны приводить к аварийному завершению приложения. Для внутренних ошибок необходимо использовать логирование. Рекомендуется использовать idiomatic Go error handling: оборачивание ошибок, `errors.Is` и `errors.As` там, где это уместно.

### 16. Клиент сервиса распознавания речи

В связи с ограничением доступа к SaluteSpeech API для новых клиентов, SaluteSpeech API не является обязательной интеграцией для успешной защиты проекта. Обязательным требованием становится не использование конкретного внешнего сервиса, а корректное проектирование слоя распознавания речи.

Необходимо реализовать абстрактный speech-клиент через интерфейс. Клиент распознавания должен позволять:
*   принять файл на обработку;
*   получить статус обработки (если реализация предполагает асинхронный внешний API);
*   получить результат распознавания;
*   обработать ошибку распознавания;
*   вернуть результат в бизнес-логику в едином формате.

В проекте должна быть минимум одна рабочая реализация speech-клиента:
1.  Тестовая реализация, возвращающая заранее подготовленную транскрипцию;
2.  Или реальная интеграция с внешним API распознавания речи (если доступ есть у участника).

Тестовая реализация обязательна, если у участника нет доступа к реальному сервису распознавания речи. Бизнес-логика приложения не должна зависеть от конкретного поставщика API. Выбор реализации клиента должен быть вынесен в конфигурацию.

*Примеры вариантов конфигурации:* `speech_provider=mock`, `speech_provider=yandex_speech_api`, `speech_provider=custom`.

### 17. Использование SaluteSpeech API

SaluteSpeech API может использоваться как дополнительная реализация speech-клиента при наличии действующего доступа. Использование SaluteSpeech API не является обязательным условием успешной защиты проекта.

> **Важно:** по информации в документации SaluteSpeech API, с 15 июля 2026 года подключение для новых клиентов недоступно, продажа пакетов и продление Freemium-тарифа прекращены. Ранее приобретённые пакеты доступны до конца срока действия или до полного исчерпания лимита.
> *Источник: документация Speech API для физических лиц*

Отсутствие доступа к SaluteSpeech API не должно снижать оценку участника, если в проекте реализованы:
*   интерфейс speech-клиента;
*   рабочая тестовая реализация клиента;
*   корректная асинхронная обработка задачи;
*   сохранение статусов и ошибок;
*   возможность заменить тестовую реализацию на реальный клиент без изменения бизнес-логики.

В качестве дополнительной реализации speech-клиента может использоваться любой доступный и согласованный сервис распознавания речи (например, Yandex SpeechKit), если у участника есть действующий доступ.

### 18. LLM-клиент

Для получения краткой выжимки и ответов на вопросы необходимо реализовать абстрактный LLM-клиент через интерфейс.

В качестве реализации может использоваться:
*   GigaChat API (если у участника есть доступ);
*   Тестовая реализация, возвращающая заранее подготовленную выжимку и ответы;
*   Иной LLM-клиент, согласованный с преподавателем или экспертом.

Обязательным является наличие минимум одной рабочей реализации LLM-клиента. Бизнес-логика не должна зависеть от конкретного LLM-поставщика.

LLM-клиент должен уметь:
*   сформировать краткую выжимку по транскрипции;
*   ответить на вопрос пользователя по переданному контексту;
*   вернуть ошибку в едином формате;
*   корректно обрабатывать таймауты и недоступность внешнего сервиса (если используется реальный API).

### 19. Тестовый режим и заглушки

Для разработки, тестирования и защиты проекта необходимо предусмотреть тестовый режим внешних клиентов.

**В тестовом режиме:**
*   speech-клиент возвращает заранее подготовленную транскрипцию;
*   LLM-клиент возвращает заранее подготовленную краткую выжимку или ответ;
*   внешние API не вызываются.

На защите необходимо уметь объяснить:
*   где в проекте используются реальные клиенты;
*   где используются заглушки;
*   как одна реализация заменяется другой;
*   почему такая архитектура упрощает тестирование;
*   почему бизнес-логика не зависит от конкретного внешнего сервиса.

### 20. Логирование и диагностика

### 21. Тестирование

В проекте должны быть unit-тесты и интеграционные тесты.

#### 21.1. Unit-тесты
Unit-тестами необходимо покрыть ключевую бизнес-логику:

*   работу с тестовым speech-клиентом;
*   работу с тестовым LLM-клиентом.

#### 21.2. Интеграционные тесты
Интеграционные тесты должны проверять связку бизнес-логики и PostgreSQL. Желательно покрыть сценарии:
*   создание встречи + создание задачи + сохранение статуса;
*   сохранение транскрипции и краткой выжимки;
*   поиск по сохранённым данным;
*   проверка разграничения данных пользователей;
*   сохранение ошибки и перевод задачи в статус `failed`.

Интеграционные тесты могут использовать тестовую базу данных, контейнер с PostgreSQL или иной согласованный способ запуска тестовой среды. Использование реальных внешних API в автотестах не требуется и не рекомендуется.

#### 21.3. Проверка конкурентного поведения
На защите участник должен показать, как проверялась корректность конкурентного кода: запуск `go test -race`, тесты на timeout, корректную отмену обработки и соблюдение лимита параллелизма или иной обоснованный способ проверки.
